# Example clients of the node API

Small, self-contained programs that talk to a Credits node through its API, one per language.
They all do the same things, with the same command line and the same output, so they can be read
side by side (smart contracts: see [Smart contracts](#smart-contracts) and [samples/contracts](../contracts/)):

| Command | API calls | What it prints |
|---|---|---|
| `status` | `SyncStateGet`, `PoolListGet(0, 1)`, `WalletsGet(0, 1, …)` | last block, current round, hash and time of the last block, number of wallets with a balance |
| `balance <address>` | `WalletBalanceGet` | the wallet's CS balance |
| `blocks [n]` | `PoolListGet(0, n)` | the last n blocks (default 10): sequence, hash, transaction count, time |
| `tx <address> [n]` | `TransactionsGet` | the wallet's transaction count and its last n transactions (default 10) |
| `transfer <key-file> <to> <amount>` | `WalletTransactionsCountGet`, `TransactionFlow` | builds, signs (ed25519) and sends a CS transfer |
| `sign <key-file> <to> <amount> <inner-id>` | none | builds and signs the same transfer offline and prints the signed bytes and the signature |
| `deploy <key-file> <Contract.java>` | `SmartContractCompile`, `WalletTransactionsCountGet`, `TransactionFlow`, `SmartContractGet` | compiles a Java contract on the node, signs and sends the deploy, waits for it and prints the contract's address |
| `call <key-file> <contract> <method> [args…]` | `SmartContractGet`, `ContractAllMethodsGet`, `WalletTransactionsCountGet`, `TransactionFlow` | calls a method in a signed transaction, with the arguments in the types the method declares, and prints its return value |
| `get <contract> <method> [args…]` | `SmartContractGet`, `ContractAllMethodsGet`, `TransactionFlow` (`forgetNewState`) | runs a method as a getter: free, nothing is sent, nothing changes; prints the value |
| `methods <contract>` | `SmartContractGet`, `ContractAllMethodsGet` | the contract's public methods with their argument types |

| Language | Directory | Thrift code | Libraries |
|---|---|---|---|
| Python 3 | [python/](python/) | read from the IDL at run time (thriftpy2) | thriftpy2, PyNaCl, base58; blake2s from `hashlib` |
| Go | [go/](go/) | `go generate` | apache/thrift 0.19.0, mr-tron/base58, golang.org/x/crypto (blake2s); ed25519 from the standard library |
| Java 17 | [java/](java/) | generated by Maven | libthrift 0.19.0, Bouncy Castle (ed25519, blake2s) |
| Rust | [rust/](rust/) | generated by `build.rs` | thrift 0.17.0, ed25519-dalek, bs58, blake2 |
| C# (.NET 8) | [csharp/](csharp/) | generated by MSBuild | ApacheThrift 0.19.0, BouncyCastle.Cryptography (ed25519, blake2s) |
| JavaScript (Node.js 18+) | [javascript/](javascript/) | `npm install` | thrift 0.19.0; ed25519 and blake2s from `node:crypto` |

The C++ sample that was here (`samples/api-client`, 2020) was removed: it only called
`SyncStateGet` against a hard-coded address, and it no longer built. A C++ client builds against the
same generated code the node uses (`api/` in this repository).

## The API

- Thrift, **binary protocol, buffered transport** (no framing), on the port set by `port` in the
  `[api]` section of the node's `config.ini` (9090 by default). Keep that port local or behind a
  firewall: the API is not authenticated.
- The definitions are in [third-party/thrift-interface-definitions](../../third-party/thrift-interface-definitions)
  (a git submodule: `git submodule update --init third-party/thrift-interface-definitions`):
  `api.thrift` (the service `API` and its structures), which includes `general.thrift`
  (`Amount`, `APIResponse`, `Variant`…). Every result has a `status` (`code` 0 for success, with a
  `message` otherwise).
- The generated code is not committed: each sample generates it from the IDL when it builds, with
  the **Thrift compiler 0.19.0** (`apt install thrift-compiler` on Ubuntu 24.04, or a release from
  [thrift.apache.org](https://thrift.apache.org/download)), matching the 0.19.0 runtime libraries
  the samples pin. Another compiler version (`brew install thrift` installs the latest) wants the
  runtime library of the same version.
  The compiler in `third-party/thrift` is the node's own fork (1.0.0-dev) and is not needed here.
- A pruned node keeps only its latest blocks: `tx` there prints the wallet's transaction count but
  usually no transactions. Ask a full node for history.

## Addresses, amounts, keys

- **Addresses** are ed25519 public keys (32 bytes) written in base58, e.g.
  `u6PJ8DtQuPFnfmwHbGFULQ4u4EgjDiyYKjVEsynXq2w`. The API takes them as raw bytes.
- **Amounts** (`general.Amount`) are `integral` (i32) plus `fraction` (i64) in units of 10^-18 CS.
  The samples parse and print them exactly, without floating point.
- **Key files** hold a base58 ed25519 secret key on one line, as the node's `NodePrivate.txt`:
  64 bytes, the 32-byte seed followed by the 32-byte public key. A bare 32-byte seed is accepted
  as well. The public key, and so the source address, is derived from the seed; with 64 bytes the
  samples check that both halves agree.
  [testdata/test-key.txt](testdata/test-key.txt) is a throwaway key for the tests (seed 0, 1, …, 31):
  never send funds to it.

## Transfers

**`transfer` signs and sends a real transaction: on mainnet it spends real CS.** Try it on a
private or test network first (see [ci/testnet](../../ci/testnet)), or against the fake node below.

What the samples do, the same way as [ci/testnet/fund.py](../../ci/testnet/fund.py):

1. the inner id (replay protection) is the sender's last one + 1, from
   `WalletTransactionsCountGet` (a wallet the node has never seen answers "not found": inner id 1);
2. the signature is ed25519 over the node's serialization for signing
   (`csdb::Transaction::to_byte_stream_for_sig`), little endian, 86 bytes for a plain transfer:

   | Bytes | Field |
   |---|---|
   | 6 | inner id |
   | 32 | source public key |
   | 32 | target public key |
   | 4 + 8 | amount: integral (i32), fraction (u64) |
   | 2 | max fee, `csdb::AmountCommission` 16-bit encoding (5-bit exponent, 10-bit mantissa) |
   | 1 | currency (1 = CS) |
   | 1 | number of user fields (0) |

3. the `Transaction` sent to `TransactionFlow` carries the same fields, plus `balance` 0,
   `timeCreation` (ms), empty `userFields`, `type` `TT_Transfer` and the signature. The max fee is
   1 CS, the most the sender accepts; the node charges the actual fee (about 0.0087 CS) and
   returns it.

`sign` prints what `transfer` would send for a given inner id, without a node. All samples print the
same bytes and signature as [testdata/sign-expected.txt](testdata/sign-expected.txt) for
`sign testdata/test-key.txt u6PJ8DtQuPFnfmwHbGFULQ4u4EgjDiyYKjVEsynXq2w 12.5 7`.

[testdata/fake_node.py](testdata/fake_node.py) stands in for a node: it answers
`WalletTransactionsCountGet` and accepts a `TransactionFlow` only when the transfer is well formed
and its signature is valid over the fields received. It sends nothing anywhere:

```sh
python3 samples/clients/testdata/fake_node.py --port 19090 &
python3 samples/clients/python/credits_client.py --node 127.0.0.1:19090 \
    transfer samples/clients/testdata/test-key.txt u6PJ8DtQuPFnfmwHbGFULQ4u4EgjDiyYKjVEsynXq2w 12.5
```

The workflow [samples.yml](../../.github/workflows/samples.yml) builds every sample and runs `sign`
and `transfer` against the fake node; it never calls mainnet.

## Smart contracts

**`deploy` and `call` sign and send real transactions: on mainnet they spend real CS.** The
contract examples in [samples/contracts](../contracts/) explain how contracts are written, what
getters, fees and `payable()` are, and are deployed with these commands on a private network by CI.

- **deploy**: the node's executor compiles the source (`SmartContractCompile`); the client derives
  the address the node will give the contract, as `SmartContracts::get_valid_smart_address` does:
  blake2s-256 of the deployer's public key, the 6-byte inner id and the byte code of every class
  in order. The deploy transaction targets that address.
- **The invocation** (`SmartContractInvocation`: method, params, usedContracts, forgetNewState,
  the deploy for a deploy, version 1) travels with the transaction and is also its one user
  field: its Thrift binary serialization. The signature covers the transfer fields described above
  with amount 0 and max fee 10 CS, then `01` (one user field), the serialization's length (u32)
  and the serialization. The node serializes the invocation it received again to check the
  signature, so the clients set every field the IDL does not mark optional (an empty
  `usedContracts`, for one): a field left out would serialize differently there.
- **Arguments** are typed as the method declares them, read from `ContractAllMethodsGet` with the
  contract's byte code: `java.lang.String` → `v_string`, `java.math.BigDecimal` → `v_big_decimal`,
  `int` → `v_int`, `long` → `v_long`, `boolean` → `v_boolean` (`true`/`false`), `double` →
  `v_double`, their wrappers → the `_box` variants, `byte[]` → `v_byte_array` (hex). With
  overloads the method with as many arguments as given is used. The node refuses a call no method
  matches, and a client refuses text that is not of the declared type, before sending anything.
- **Return values** print the same in every client: `true`/`false`, numbers and strings as they
  are, `void` for a void method, hex for `byte[]`.
- **A call that throws** is answered with an error ("call to contract failed"); the client exits 1.
  It still pays its fee.
- **get** sends a `TransactionFlow` with `forgetNewState=true`, an all-zero source and signature:
  the node runs the method on its own executor against the current state and forgets the result.
- **Paying a contract** is a plain `transfer` to its address: the node calls its `payable()`.

The fake node also plays a node with one made-up contract (`add(int)`, `setNote(String)`,
`paidBy(String)`, `isOpen()`): it accepts a deploy only to the derived address, with a valid
signature over the invocation as the node serializes it, and calls only with the declared Variant
types. `CONTRACTS=1 testdata/check.sh <client>` checks `deploy`, `call` and `get` against it.
